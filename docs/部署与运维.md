## 0. 一句话拓扑

单机一台（2C4G 起步），四个容器，**Caddy 做边缘**：自动 HTTPS + 托管前端静态 + 把 `/v1/*` 同源反代给后端，前端因此**零 CORS**。

```
                 Internet
                    │  :443 (自动 HTTPS) / :80
            ┌───────▼────────┐
            │     caddy      │  边缘：TLS + 静态(SPA) + 反代
            │  (inkling-web) │
            └───┬────────┬───┘
       /v1/* →  │        │  其余 → 静态文件 /srv (Nuxt 静态产物)
            ┌───▼────┐   └─────────────►  index.html (SPA history 回退)
            │  api   │  NestJS :3001（不对外暴露）
            │(inkling│  启动时 prisma migrate deploy → node dist/main.js
            │ -api)  │
            └─┬────┬─┘
      ┌───────▼┐ ┌─▼────────┐
      │postgres│ │  redis   │  命名卷持久化
      │  :5432 │ │  :6379   │  pg-data / redis-data
      └────────┘ └──────────┘
```

配套文件：

| 文件 | 作用 |
|---|---|
| [`deploy/api.Dockerfile`](../deploy/api.Dockerfile) | API 生产镜像（NestJS + Prisma，**启动时应用迁移**） |
| [`deploy/web.Dockerfile`](../deploy/web.Dockerfile) | 边缘镜像（Nuxt 静态产物 → Caddy 托管 + 反代） |
| [`deploy/Caddyfile`](../deploy/Caddyfile) | 边缘路由：`/v1/*`→api，其余→SPA |
| [`deploy/docker-compose.prod.yml`](../deploy/docker-compose.prod.yml) | 四服务编排 |
| [`deploy/env.production.example`](../deploy/env.production.example) | 生产 `.env` 模板 |
| [`.dockerignore`](../.dockerignore) | 排除宿主 `node_modules` 等（**关键**：避免 win32 二进制进 linux 镜像） |
| [`.github/workflows/images.yml`](../.github/workflows/images.yml) | CI 离线验证两镜像可构建 |

## 1. 服务器选型与前置

| 项 | 建议 |
|---|---|
| 规格 | **2C4G / 60G SSD**（更稳 2C8G）。冷启动期足够。 |
| 系统 | Ubuntu 22.04 LTS |
| 节点 | 香港 / 新加坡（面向海外华人/留学生，延迟与合规均衡） |
| 软件 | Docker Engine + Compose 插件（`docker compose` v2） |
| 网络 | 开放 80 / 443；22 仅限管理 IP |
| 域名 | 一个 A 记录指向服务器公网 IP（Caddy 签证书前必须先生效） |

安装 Docker（Ubuntu，参考）：

```bash
curl -fsSL https://get.docker.com | sh
sudo usermod -aG docker $USER   # 重新登录生效
docker compose version          # 确认 v2
```

> 构建在哪做？两种都行：**(a) 直接在服务器 `up -d --build`**（最简单，2C4G 够编译，首次较慢）；**(b) 在 CI/本地构建镜像推私有 registry，服务器只拉取运行**（生产推荐，省服务器算力）。本手册默认 (a)；(b) 见 §10。

## 2. 环境变量与密钥清单

复制模板后**逐项填写**（仓库根目录）：

```bash
cp deploy/env.production.example .env
```

| 变量 | 是否密钥 | 生产取值要点 |
|---|---|---|
| `SITE_ADDRESS` | 否 | 正式域名（自动 HTTPS）；本机联测填 `:80` |
| `POSTGRES_USER` / `POSTGRES_DB` | 否 | 默认 `inkling` 即可 |
| `POSTGRES_PASSWORD` | **是** | 强随机；与 `DATABASE_URL` 中保持一致 |
| `DATABASE_URL` | **是** | host 用 **`postgres`**（服务名）非 localhost：`postgresql://inkling:<pwd>@postgres:5432/inkling?schema=public` |
| `REDIS_URL` | 否 | `redis://redis:6379`（服务名） |
| `JWT_SECRET` | **是** | `openssl rand -base64 48` 生成的长随机串 |
| `JWT_ACCESS_TTL` / `JWT_REFRESH_TTL` | 否 | `15m` / `30d` |
| `API_PORT` | 否 | `3001`（仅容器内，不外暴） |
| `WEB_ORIGIN` | 否 | 正式域名；同源反代下浏览器不触发 CORS，仅直连 API 时生效 |
| `DELIVERY_HOURS_SCALE` | 否 | **必须 `1`**——真实 4–96h 距离精算。设 0 会让笔友信秒到，**破坏慢节奏核心体验** |
| `THROTTLE_TTL_MS` / `THROTTLE_LIMIT` | 否 | 限流窗口/全局上限（默认 `60000`/`300`，按 IP×路由）。校园/公司 NAT 共用 IP 群体勿设太低；`/v1/auth/*` 代码内已收紧 8/min。**生产勿设 `THROTTLE_DISABLED=1`** |
| `LETTER_POOL_DELAY_SECONDS` 等节奏参数 | 否 | 默认即可，按运营调 |
| `MODERATION_PROVIDER` | 否 | MVP `local`；接第三方多语种 API 时 `remote` + 填 `MODERATION_API_*`（C 档） |
| `MIN_AGE_HARD_FLOOR` / `GUARDIAN_MODE_BELOW_AGE` | 否 | `13` / `18`（按目标地法定，见 [合规文档](合规与本地化-海外.md)） |

**前端三个值在构建期固化进 web 镜像**（不在运行时 `.env`）：`NUXT_PUBLIC_API_BASE=/v1`、`NUXT_PUBLIC_USE_MOCK=0`、`NODE_ENV=production`。改它们须**重建 web 镜像**。生产构建下前端 Mock 已自动关闭（`import.meta.dev=false`），但**切勿手动设 `NUXT_PUBLIC_USE_MOCK=1`**，否则全站连不到真后端。

> `.env` 已被 `.gitignore` 忽略，**绝不提交**。密钥建议同时存进密码管理器/服务器密钥管理。

## 3. 首次部署（从零到可用）

```bash
# 1) 取代码
git clone <repo> inkling && cd inkling

# 2) 配置（见 §2，填完所有 CHANGE_ME）
cp deploy/env.production.example .env
vim .env

# 3) DNS：确认 A 记录已指向本机公网 IP 且已生效（dig <域名> 验证），否则 Caddy 签证书会失败

# 4) 构建并起全栈（务必在仓库根目录执行，让 --env-file 与 env_file 指向同一 .env）
docker compose -f deploy/docker-compose.prod.yml --env-file .env up -d --build

# api 容器启动时会自动 `prisma migrate deploy` 建表（首次会套用全部 3 个 migration）

# 5) 注入种子写信人（一次性；api 镜像含完整依赖，可直接 exec）
docker compose -f deploy/docker-compose.prod.yml --env-file .env exec api pnpm prisma:seed
#   ⚠️ 种子账号默认密码 inkling123，仅为"漂流邮局"系统写信人。生产前请评估是否需要/改密（见检查清单）

# 6) 验活
curl -fsS https://<域名>/v1/health         # → {"ok":true,"data":{"status":"ok"}}
curl -fsS https://<域名>/v1/health/ready    # → checks.db / checks.redis 均 true
```

打开 `https://<域名>` 应进入登录页，注册→完善名片→漂流海打捞种子信→拆封→回信结缘全链路应可走通。

## 4. 健康探针

后端已内置（公开端点，无需鉴权）：

| 端点 | 语义 | 用途 |
|---|---|---|
| `GET /v1/health` | 存活：进程在跑即 200，不查依赖 | 容器/反代心跳、重启判定 |
| `GET /v1/health/ready` | 就绪：DB + Redis 均可用才 200，否则 **503** | 放流量前判定、上线后探活 |

- api 容器 `HEALTHCHECK` 已用 `/v1/health/ready`（`docker compose ps` 可见 healthy/unhealthy）。
- 接入外部 Uptime 监控时探 `https://<域名>/v1/health`。

## 5. 数据备份与恢复

数据全在两个命名卷：`pg-data`（**权威数据**）、`redis-data`（锁/计数，可重建，非权威）。**只有 Postgres 必须备份。**

**每日逻辑备份（host crontab）：**

```bash
# /etc/cron.d/inkling-backup —— 每日 03:30 备份并保留 14 天
30 3 * * * root cd /opt/inkling && docker compose -f deploy/docker-compose.prod.yml --env-file .env exec -T postgres \
  pg_dump -U inkling inkling | gzip > /opt/inkling/backups/inkling-$(date +\%F).sql.gz \
  && find /opt/inkling/backups -name 'inkling-*.sql.gz' -mtime +14 -delete
```

**恢复演练（务必上线前演练一次）：**

```bash
# 在测试库恢复，确认备份可用
gunzip -c backups/inkling-2026-06-20.sql.gz | \
  docker compose -f deploy/docker-compose.prod.yml --env-file .env exec -T postgres psql -U inkling -d inkling
```

> 异地：定期把 `backups/` 同步到对象存储/另一台机（C 档接对象存储后可自动化）。

## 7. 伸缩与已知约束（重要）

| 约束 | 说明 | 何时需要处理 |
|---|---|---|
| **api 必须单副本** | 时间驱动用**进程内** `@nestjs/schedule` 轮询；采用**启动时迁移**；**限流计数为进程内内存 Map（非 Redis）**。多副本会重复触发调度、并发迁移，且限流上限被静默放大 N 倍。 | 横向扩 api 前必做：scheduler 抽成单独 worker（或分布式领导选举）、迁移改独立一次性 Job（见 §8 注）、**限流接 Redis storage**（`@nest-lab/throttler-storage-redis`，复用现有 redis 容器与 `REDIS_URL`） |
| 调度幂等 | 现有 scheduler 已用 `count===1` 守卫 + `warnedAt`/`recycledAt` 去重，单副本下安全 | — |
| Redis 单实例 | 仅做锁/计数，非权威数据 | 高可用期再上 Sentinel/集群 |
| 镜像偏大 | 为构建稳健，运行镜像保留了完整依赖（含 devDeps，便于容器内跑 migrate/seed） | 优化期改 `pnpm deploy --prod` 瘦身（注意 Prisma 生成产物随附） |
| GDPR 导出 | 现为接口内联返回结构化 JSON | 大体量用户期改异步打包 + 对象存储下载（C 档） |

## 8. 升级 / 发布流程（日常）

```bash
cd /opt/inkling
git pull
docker compose -f deploy/docker-compose.prod.yml --env-file .env up -d --build
# 仅重建有变更的镜像；api 重启时自动套用新增（additive）migration
```

- **数据库变更原则**：Prisma migration **只增不改**（additive：加表/加列/加索引）。新增列给默认值或可空，确保**旧代码 + 新表结构**兼容——这是回滚能安全的前提。
- 破坏性变更（删列/改类型/改语义）须走两步发布：① 先发兼容新旧的中间版本；② 数据迁移完成后再清理。**严禁单步删除在用字段。**
- > 注：当前为单副本「启动时迁移」。若改多副本，迁移须抽成独立一次性任务（`docker compose run --rm api pnpm prisma:deploy`）并在所有副本启动前完成，避免并发迁移。

## 9. 回滚预案 🔴

**先判断：本次发布有没有破坏性 DB 迁移？**

```
                 出问题，要回滚
                       │
        ┌──────────────┴───────────────┐
        │ 本次只含 additive 迁移？        │
        └──────┬───────────────┬────────┘
             是 │             否 │（含删列/改类型/改语义）
               ▼               ▼
   【代码级回滚，最快】   【代码 + 数据回滚】
   旧代码兼容新表结构    须先恢复备份，再回滚代码
```

**A. 代码级回滚（additive 场景，分钟级）**

```bash
cd /opt/inkling
git checkout <上一个可用 tag/commit>
docker compose -f deploy/docker-compose.prod.yml --env-file .env up -d --build
```
新增的表/列对旧代码无害（不读即可），无需动数据库。
> 提速建议：发布时给镜像打 **git sha 标签**（而非只用 `:latest`），回滚直接切回旧 tag 免重建。改法见 §10。

**B. 代码 + 数据回滚（破坏性迁移场景）**

1. **立即止血**：`docker compose ... stop api`（停写）。
2. **恢复数据库**：从**发布前**的 `pg_dump` 备份恢复（见 §5）。→ 所以**任何破坏性发布前必须先手动备份一次**。
3. **回滚代码**：切回旧 tag 重建。
4. 起服务，验活（§4）。

**C. 紧急全停（保数据）**

```bash
docker compose -f deploy/docker-compose.prod.yml down   # 停容器，命名卷保留（数据不丢）
# 排查后再 up -d
```
> `down -v` 会**删卷丢数据**，除非确认要清空，否则绝不加 `-v`。

**回滚前置（务必满足，否则 B 无法执行）：** 破坏性发布前已 `pg_dump` 备份 + 已演练过恢复 + 镜像可回退（git tag 或 registry 旧 tag）。

## 11. 故障排查

| 现象 | 可能原因 / 处理 |
|---|---|
| Caddy 一直签不出证书 | DNS 未生效、80 端口被占/被防火墙挡、`SITE_ADDRESS` 写成了 `:80`（明文不签证书）。`docker compose logs caddy` 看 ACME 报错 |
| 前端能开但所有请求失败 | 误设 `NUXT_PUBLIC_USE_MOCK=1` 重建过镜像；或 Caddy 未把 `/v1/*` 反代到 api。检查 web 镜像构建期 ENV 与 Caddyfile |
| api 起不来，日志卡在迁移 | `DATABASE_URL` host 写成 localhost（应为 `postgres`）、密码不一致、postgres 未 healthy。`docker compose ps` 看依赖 |
| `/v1/health/ready` 503 | db 或 redis 不通——按 `checks` 字段定位；多为连接串/容器未就绪 |
| 构建拉不到 Prisma 引擎/依赖 | 网络抖动（ECONNRESET），重试 `up -d --build`；CI 上一般稳定 |
| 注册/登录报 CORS | 仅在**绕过 Caddy 直连 api** 时出现；走正常同源域名不会。需要直连则把来源加进 `WEB_ORIGIN` |
